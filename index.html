Brute Force — Why O(n!)?

Fix the starting city (say A). Then count the choices for each next city:

  • 1st choice: n − 1 cities
  • 2nd choice: n − 2 cities
  • 3rd choice: n − 3 cities
  • …
  • Last choice: 1 city

(n−1) · (n−2) · … · 1 = (n−1)! possible tours

Every tour is generated, evaluated, and compared against the best so far. Nothing is skipped — which is exactly why it becomes impractical so quickly.

Held–Karp — Why O(n²·2ⁿ)?

Instead of re-solving the same subproblem many times, Held–Karp memoizes it. A subproblem is a state:

dp[mask][i] = cheapest cost to start at A, visit exactly the cities in mask, and end at i

  • There are 2ⁿ possible subsets (masks) of cities.
  • For each subset, we consider up to n ending cities i.
  • Each state tries transitions from up to n previous cities.

2ⁿ subsets × n endings × n transitions = O(n²·2ⁿ)

DP never recomputes a state — repeated work in brute force becomes a single table lookup.

Branch & Bound — Why can it be faster?

It explores the same search tree as brute force, but it prunes branches that provably cannot beat the best tour found so far.

For a partial route it computes a lower bound: the cheapest any completion of this route could possibly be. If:

lower bound ≥ current best → PRUNE

The lower bound in this visualizer = cost so far + the cheapest possible way to leave every unvisited city (minimum outgoing edge), plus the cheapest return to the start. No real completion can be cheaper than this, so pruning is always safe.

Important: worst-case complexity is still exponential. Pruning helps on typical instances, but a hostile instance can force it to explore nearly everything.
